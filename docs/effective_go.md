# Effective Go — полный конспект

## Введение

Go — новый язык. Хотя он заимствует идеи из существующих языков, он обладает необычными свойствами, которые делают эффективные программы на Go отличными по характеру от программ, написанных на его родственниках. Прямой перевод кода на C++ или Java в Go вряд ли даст удовлетворительный результат — программы на Java пишутся на Java, а не на Go. С другой стороны, если думать о проблеме с точки зрения Go, код может получиться успешным, хотя и совершенно другим. Другими словами, чтобы хорошо писать на Go, важно понимать его свойства и идиомы. Также важно знать установленные соглашения для именования, форматирования, построения программ и т.д., чтобы программы, которые вы пишете, были легко понятны другим программистам на Go.

Этот документ даёт советы по написанию ясного, идиоматичного кода на Go. Он дополняет спецификацию языка, «Tour of Go» и «How to Write Go Code», все из которых следует прочитать в первую очередь.

**Примечание (добавлено в 2022 году):** этот документ был написан для релиза Go в 2009 году и с тех пор не обновлялся существенно. Он не охватывает дженерики, модули и многое другое из того, что было добавлено в язык и библиотеки в последующие годы. Мы оставляем его доступным, потому что он всё ещё даёт хорошие советы по использованию ядра языка.

### Форматирование

Вопросы форматирования — самые спорные, но наименее значимые. Люди могут адаптироваться к разным стилям форматирования, но лучше, если им не приходится этого делать, и меньше времени тратится впустую, если все придерживаются одного стиля. Проблема в том, как подойти к этому утопическому состоянию без длинного руководства по стилю.

В Go мы применяем необычный подход и позволяем машине заботиться о большинстве вопросов форматирования. Программа `gofmt` (также доступная как `go fmt`, она работает на уровне пакета, а не исходного файла) читает программу на Go и выдаёт исходный код в стандартном стиле отступов и вертикального выравнивания, сохраняя и при необходимости переформатируя комментарии. Если вы хотите узнать, как справиться с какой-то новой ситуацией с layout, запустите `gofmt`; если ответ кажется неправильным, переставьте программу (или сообщите об ошибке в `gofmt`), не ищите обходные пути.

В качестве примера: нет необходимости тратить время на выравнивание комментариев к полям структуры. `gofmt` сделает это за вас. Учитывая объявление

```go
type T struct {
    name string // name of the object
    value int // its value
}
```

`gofmt` выровняет столбцы:

```go
type T struct {
    name    string // name of the object
    value   int    // its value
}
```

Все стандартные пакеты Go отформатированы с помощью `gofmt`.

Остаются некоторые детали форматирования. Очень кратко:

**Отступы.** Мы используем табы для отступов, и `gofmt` выдаёт их по умолчанию. Пробелы используем только при необходимости.

**Длина строк.** В Go нет ограничения на длину строки. Не беспокойтесь о переполнении перфокарты. Если строка кажется слишком длинной, перенесите её и сделайте отступ с дополнительным табом.

**Скобки.** Go требует меньше скобок, чем C и Java: управляющие структуры (`if`, `for`, `switch`) не имеют скобок в своём синтаксисе. Также иерархия приоритетов операторов короче и яснее, чем в C. Так что

```
x<<8 + y<<16
```

означает то, что подразумевает пробел, в отличие от других языков.

### Комментарии

Go предоставляет блочные комментарии в стиле C `/* */` и строчные комментарии в стиле C++ `//`. Строчные комментарии — норма; блочные комментарии в основном используются как комментарии к пакетам, но также полезны внутри выражений или для отключения больших участков кода.

Комментарии, которые появляются перед объявлениями верхнего уровня без промежуточных переводов строк, считаются документирующими само объявление. Эти «doc comments» — основная документация для данного пакета или команды Go. Дополнительную информацию о комментариях к документации можно найти в разделе «Doc comments».

### Имена

Имена в Go имеют такое же значение, как и в любом другом языке. Они даже имеют семантический эффект: видимость имени за пределами пакета определяется тем, является ли его первый символ заглавной буквой. Поэтому стоит потратить немного времени на обсуждение соглашений об именовании в программах на Go.

#### Имена пакетов

Когда пакет импортируется, его имя становится аксессором для содержимого. После

```go
import "bytes"
```

импортирующий пакет может говорить о `bytes.Buffer`. Полезно, если все, кто использует пакет, могут использовать одно и то же имя для ссылки на его содержимое, что подразумевает, что имя пакета должно быть хорошим: коротким, лаконичным, вызывающим. По соглашению, пакеты получают имена в нижнем регистре, состоящие из одного слова; не должно быть необходимости в подчёркиваниях или mixedCaps. (Имена пакетов с несколькими словами используются редко, но когда они используются, применяется нижний регистр без подчёркиваний, например, `encoding/base64`.) Пакет в `src/encoding/base64` импортируется как `"encoding/base64"`, но имеет имя `base64`, а не `encoding_base64` и не `encodingBase64`.

Импортирующий пакет будет использовать имя для ссылки на содержимое, поэтому экспортируемые имена в пакете могут использовать этот факт, чтобы избежать повторений. (Не используйте соглашение `import .`, которое может упростить тесты, запускаемые вне пакета, но в остальном его следует избегать.) Например, тип буферизованного читателя в пакете `bufio` называется `Reader`, а не `BufReader`, потому что пользователи видят его как `bufio.Reader`, что является ясным, лаконичным именем. Более того, поскольку импортированные сущности всегда адресуются по имени пакета, `bufio.Reader` не конфликтует с `io.Reader`. Аналогично, функция для создания новых экземпляров `ring.Ring`, которая является определением конструктора в Go, обычно называется `NewRing`, но поскольку `Ring` — единственный экспортируемый тип в пакете, а пакет называется `ring`, клиенты видят её как `ring.New`. Используйте структуру пакета, чтобы выбрать хорошие имена.

Ещё один короткий пример — `once.Do` из `sync` (не `once.DoOrWaitUntilDone`). Длинные имена не делают вещи более читаемыми автоматически. Полезный документ-комментарий может быть более ценным, чем длинное имя.

#### Геттеры

Go не предоставляет автоматической поддержки геттеров и сеттеров. Нет ничего плохого в том, чтобы предоставлять геттеры и сеттеры самостоятельно, и часто это уместно, но идиоматично называть геттер `Owner` (с заглавной буквы, экспортируемый), а не `GetOwner`. Использование имени с заглавной буквы для экспорта обеспечивает возможность отличить поле от метода. Если вам нужна функция-сеттер, назовите её `SetOwner`. Оба имени хорошо читаются:

```go
owner := obj.Owner()
if owner != user {
    obj.SetOwner(user)
}
```

#### Имена интерфейсов

По соглашению, одно-методные интерфейсы именуются по имени метода плюс суффикс `-er` или аналогичная модификация для образования существительного-агента: `Reader`, `Writer`, `Formatter`, `CloseNotifier` и т.д.

Существует ряд таких имён, и соблюдение этого соглашения и имён функций, которые они захватывают, полезно. `Read`, `Write`, `Close`, `Flush`, `String` и т.д. имеют канонические подписи и значения. Чтобы избежать путаницы, не давайте вашему методу одно из этих имён, если оно не имеет той же подписи и значения. И наоборот, если ваш тип реализует метод с тем же значением, что и метод хорошо известного типа, дайте ему то же имя и подпись; назовите ваш метод-конвертер строк `String`, а не `ToString`.

#### MixedCaps

Наконец, соглашение в Go — использовать `MixedCaps` или `mixedCaps`, а не подчёркивания, для написания имён из нескольких слов.

### Точки с запятой

Формально грамматика Go использует точки с запятой для завершения операторов, как в C. Но, в отличие от C, эти точки с запятой не появляются в исходном коде. Вместо этого лексер использует простое правило для автоматической вставки точек с запятой по мере сканирования, так что ввод в основном свободен от них.

Правило таково: если последний токен перед новой строкой — это идентификатор (который включает слова типа `int` и `float64`), базовый литерал (число или строковая константа) или один из токенов

```
break continue fallthrough return ++ -- ) }
```

лексер всегда вставляет точку с запятой после токена. Это можно резюмировать так: «если новая строка идёт после токена, который может завершить оператор, вставьте точку с запятой».

Точку с запятой также можно опустить непосредственно перед закрывающей фигурной скобкой, так что оператор вроде

```go
    go func() { for { dst <- <-src } }()
```

не нуждается в точках с запятой. Идиоматичные программы на Go имеют точки с запятой только в таких местах, как циклы `for`, для разделения компонентов инициализации, условия и продолжения. Они также необходимы для разделения нескольких операторов в одной строке, если вы пишете код таким образом.

Одно из следствий правил вставки точек с запятой заключается в том, что нельзя ставить открывающую фигурную скобку управляющей структуры (`if`, `for`, `switch` или `select`) на следующей строке. Если вы это сделаете, точка с запятой будет вставлена перед фигурной скобкой, что может вызвать нежелательные эффекты. Пишите так:

```go
if i < f() {
    g()
}
```

а не так:

```go
if i < f()  // wrong!
{           // wrong!
    g()
}
```

### Управляющие структуры

Управляющие структуры Go связаны с C, но отличаются в важных отношениях. Нет циклов `do` или `while`, только немного обобщённый `for`. `switch` более гибок. `if` и `switch` принимают необязательный оператор инициализации, как у `for`. `break` и `continue` принимают необязательную метку для идентификации того, к чему применять. И есть новые управляющие структуры, включая type switch и многопоточный мультиплексор `select`. Синтаксис также немного отличается: нет круглых скобок, и тела всегда должны быть ограничены фигурными скобками.

#### If

В Go простой `if` выглядит так:

```go
if x > 0 {
    return y
}
```

Обязательные фигурные скобки поощряют запись простых `if` на нескольких строках. Это хорошо, особенно когда тело содержит управляющий оператор, такой как `return` или `break`.

Поскольку `if` и `switch` принимают оператор инициализации, часто можно видеть его использование для настройки локальной переменной:

```go
if err := file.Chmod(0664); err != nil {
    log.Print(err)
    return err
}
```

В библиотеках Go вы обнаружите, что когда `if` не переходит в следующий оператор — то есть тело заканчивается на `break`, `continue`, `goto` или `return` — ненужный `else` опускается:

```go
f, err := os.Open(name)
if err != nil {
    return err
}
codeUsing(f)
```

Это пример общей ситуации, когда код должен защищаться от последовательности условий ошибки. Код читается хорошо, если успешный поток управления идёт вниз по странице, устраняя случаи ошибок по мере их возникновения. Поскольку случаи ошибок обычно заканчиваются операторами `return`, результирующий код не нуждается в `else`:

```go
f, err := os.Open(name)
if err != nil {
    return err
}
d, err := f.Stat()
if err != nil {
    f.Close()
    return err
}
codeUsing(f, d)
```

#### Переобъявление и переназначение

Отступление к предыдущему разделу: в примере показано, как форма `:=` краткого объявления работает:

```go
f, err := os.Open(name)
d, err := f.Stat()
```

На первый взгляд может показаться, что `err` объявляется дважды. Но это нормально: в первой строке объявляются и `f`, и `err`. Во второй строке объявляется `d` и *переприсваивается* существующая `err`. Это означает, что вызов `f.Stat` использует существующую переменную `err`, объявленную выше, просто давая ей новое значение.

В объявлении `:=` переменная `v` может появляться, даже если она уже была объявлена, при условии:

- это объявление находится в той же области видимости, что и существующее объявление `v` (если `v` уже объявлена во внешней области видимости, объявление создаст новую переменную §),
- соответствующее значение в инициализации присваиваемо `v`, и
- есть хотя бы одна другая переменная, создаваемая объявлением.

Это необычное свойство — чистый прагматизм, облегчающий использование одного значения `err`, например, в длинной цепочке `if-else`. Вы увидите, что это используется часто.

§ Здесь стоит отметить, что в Go область видимости параметров функции и возвращаемых значений совпадает с областью видимости тела функции, хотя они появляются лексически вне скобок, окружающих тело.

#### For

Цикл `for` в Go похож на C, но не идентичен ему. Он объединяет `for` и `while`, и нет `do-while`. Есть три формы, только одна из которых содержит точки с запятой:

```go
// Like a C for
for init; condition; post { }

// Like a C while
for condition { }

// Like a C for(;;)
for { }
```

Краткие объявления упрощают объявление переменной индекса прямо в цикле:

```go
sum := 0
for i := 0; i < 10; i++ {
    sum += i
}
```

Если вы перебираете массив, срез, строку или карту, или читаете из канала, предложение `range` может управлять циклом:

```go
for key, value := range oldMap {
    newMap[key] = value
}
```

Если вам нужен только первый элемент в диапазоне (ключ или индекс), отбросьте второй:

```go
for key := range m {
    if key.expired() {
        delete(m, key)
    }
}
```

Если вам нужен только второй элемент в диапазоне (значение), используйте пустой идентификатор (подчёркивание), чтобы отбросить первый:

```go
sum := 0
for _, value := range array {
    sum += value
}
```

Для строк `range` делает больше работы для вас, разбивая отдельные кодовые точки Unicode, анализируя UTF-8. Ошибочные кодировки потребляют один байт и производят заменяющую руну U+FFFD. (Имя `rune` — это встроенный тип Go для одной кодовой точки Unicode. Дополнительные сведения см. в разделе «Runes».) Конструкция

```go
for pos, char := range "日本\x80語" { // \x80 is an illegal UTF-8 encoding
    fmt.Printf("character %#U starts at byte position %d\n", char, pos)
}
```

выводит

```
character U+65E5 '日' starts at byte position 0
character U+672C '本' starts at byte position 3
character U+FFFD '�' starts at byte position 6
character U+8A9E '語' starts at byte position 7
```

Наконец, в Go нет оператора запятой, а `++` и `--` — это операторы, а не выражения. Поэтому, если вы хотите запустить несколько переменных в `for`, вы должны использовать параллельное присваивание (хотя это исключает `++` и `--`):

```go
// Reverse a
for i, j := 0, len(a)-1; i < j; i, j = i+1, j-1 {
    a[i], a[j] = a[j], a[i]
}
```

#### Switch

`Switch` в Go более общий, чем в C. Выражения не обязательно должны быть константами или даже целыми числами; случаи оцениваются сверху вниз до нахождения совпадения, и если `switch` не имеет выражения, он переключается на `true`. Это позволяет писать `if-else-if-else` цепочки, используя `switch`. Синтаксис:

```go
func unhex(c byte) byte {
    switch {
    case '0' <= c && c <= '9':
        return c - '0'
    case 'a' <= c && c <= 'f':
        return c - 'a' + 10
    case 'A' <= c && c <= 'F':
        return c - 'A' + 10
    }
    return 0
}
```

Нет автоматического провала, но случаи могут быть представлены в виде списков, разделённых запятыми:

```go
func shouldEscape(c byte) bool {
    switch c {
    case ' ', '?', '&', '=', '#', '+', '%':
        return true
    }
    return false
}
```

Хотя они не так распространены в Go, как в некоторых других C-подобных языках, операторы `break` могут использоваться для досрочного выхода из `switch`, а иногда необходимо выйти из окружающего цикла, а не из `switch`. В Go это можно сделать, поместив метку на цикле и «разорвав» эту метку:

```go
Loop:
    for n := 0; n < len(src); n += size {
        switch {
        case src[n] < sizeOne:
            if validateOnly {
                break
            }
            size = 1
            update(src[n])
        case src[n] < sizeTwo:
            if n+1 >= len(src) {
                err = errShortInput
                break Loop
            }
            if validateOnly {
                break
            }
            size = 2
            update(src[n] + src[n+1]<<shift)
        }
    }
```

Конечно, оператор `continue` также принимает необязательную метку, но он применяется только к циклам.

Вот пример сравнения байтовых срезов, использующий два оператора `switch`:

```go
// Compare returns an integer comparing the two byte slices,
// lexicographically.
// The result will be 0 if a == b, -1 if a < b, and +1 if a > b
func Compare(a, b []byte) int {
    for i := 0; i < len(a) && i < len(b); i++ {
        switch {
        case a[i] > b[i]:
            return 1
        case a[i] < b[i]:
            return -1
        }
    }
    switch {
    case len(a) > len(b):
        return 1
    case len(a) < len(b):
        return -1
    }
    return 0
}
```

#### Type switch

`Switch` также может использоваться для определения динамического типа переменной интерфейса. Такой *type switch* использует синтаксис утверждения типа с ключевым словом `type` внутри скобок. Если `switch` объявляет переменную в выражении, переменная будет иметь соответствующий тип в каждом предложении. В этом случае также идиоматично повторно использовать имя в каждом случае, фактически объявляя новую переменную с тем же именем, но другого типа в каждом предложении:

```go
var t interface{}
t = functionOfSomeType()
switch t := t.(type) {
default:
    fmt.Printf("unexpected type %T\n", t)     // %T prints whatever type t has
case bool:
    fmt.Printf("boolean %t\n", t)             // t has type bool
case int:
    fmt.Printf("integer %d\n", t)             // t has type int
case *bool:
    fmt.Printf("pointer to boolean %t\n", *t) // t has type *bool
case *int:
    fmt.Printf("pointer to integer %d\n", *t) // t has type *int
}
```

### Функции

#### Множественные возвращаемые значения

Одна из необычных особенностей Go заключается в том, что функции и методы могут возвращать несколько значений. Эта форма может использоваться для улучшения нескольких неуклюжих идиом в C: возврата ошибок в полосе, таких как `-1` для EOF, и модификации аргумента, переданного по адресу.

В C отрицательное число сигнализирует об ошибке, а код, возвращающий количество записанных байтов, скрывает это. В Go `Write` может возвращать количество и ошибку: «Да, вы записали некоторые байты, но не все, потому что заполнили устройство». Подпись метода записи в пакете `os`:

```go
func (file *File) Write(b []byte) (n int, err error)
```

и, как говорится в документации, он возвращает количество записанных байтов и ненулевой `error`, когда `n != len(b)`. Это распространённый стиль; смотрите раздел обработки ошибок для получения дополнительных примеров.

Аналогичный подход устраняет необходимость передавать указатель на возвращаемое значение для имитации ссылочного параметра. Вот простая функция для получения числа из позиции в байтовом срезе, возвращающая число и следующую позицию:

```go
func nextInt(b []byte, i int) (int, int) {
    for ; i < len(b) && !isDigit(b[i]); i++ {
    }
    x := 0
    for ; i < len(b) && isDigit(b[i]); i++ {
        x = x*10 + int(b[i]) - '0'
    }
    return x, i
}
```

Вы можете использовать его для сканирования чисел во входном срезе `b` следующим образом:

```go
for i := 0; i < len(b); {
    x, i = nextInt(b, i)
    fmt.Println(x)
}
```

#### Именованные параметры результата

Параметры возврата или результата функции Go могут быть заданы именами и использоваться как обычные переменные. Когда они названы, они инициализируются нулевыми значениями своих типов при запуске функции; если функция выполняет оператор `return` без аргументов, текущие значения параметров результата используются в качестве возвращаемых значений.

Имена не обязательны, но они могут сделать код короче и яснее: это документация. Если мы назовём результаты `nextInt`, станет очевидно, какой из возвращаемых `int` какой:

```go
func nextInt(b []byte, pos int) (value, nextPos int) {
```

Поскольку именованные результаты инициализируются и привязаны к простому возврату, они могут упростить, а также прояснить. Вот версия `io.ReadFull`, которая хорошо их использует:

```go
func ReadFull(r Reader, buf []byte) (n int, err error) {
    for len(buf) > 0 && err == nil {
        var nr int
        nr, err = r.Read(buf)
        n += nr
        buf = buf[nr:]
    }
    return
}
```

#### Defer

Оператор `defer` в Go планирует вызов функции (отложенной функции) к выполнению непосредственно перед тем, как функция, выполняющая `defer`, вернётся. Это необычный, но эффективный способ решения ситуаций, таких как ресурсы, которые должны быть освобождены независимо от того, по какому пути функция возвращается. Канонические примеры — разблокировка мьютекса или закрытие файла.

```go
// Contents returns the file's contents as a string.
func Contents(filename string) (string, error) {
    f, err := os.Open(filename)
    if err != nil {
        return "", err
    }
    defer f.Close()  // f.Close will run when we're finished.

    var result []byte
    buf := make([]byte, 100)
    for {
        n, err := f.Read(buf[0:])
        result = append(result, buf[0:n]...) // append is discussed later.
        if err != nil {
            if err == io.EOF {
                break
            }
            return "", err  // f will be closed if we return here.
        }
    }
    return string(result), nil // f will be closed if we return here.
}
```

Отложенный вызов функции, такой как `Close`, имеет два преимущества. Во-первых, он гарантирует, что вы никогда не забудете закрыть файл, — ошибка, которую легко совершить, если позже отредактировать функцию, добавив новый путь возврата. Во-вторых, это означает, что `close` находится рядом с `open`, что гораздо яснее, чем размещение его в конце функции.

Аргументы отложенной функции (включая получателя, если функция является методом) оцениваются при *выполнении* `defer`, а не при *выполнении* вызова. Кроме того, чтобы избежать беспокойства о переменных, изменяющихся при выполнении функции, отложенные функции выполняются в порядке LIFO (последний пришёл — первый вышел). Этот пример выводит «3210»:

```go
for i := 0; i < 5; i++ {
    defer fmt.Printf("%d ", i)
}
```

Отложенные функции выполняются в порядке LIFO, поэтому этот код печатает `4 3 2 1 0`, когда функция возвращается. Более разумный пример — простой способ трассировки выполнения функции через программу. Мы могли бы написать пару простых функций трассировки, подобных этим:

```go
func trace(s string)   { fmt.Println("entering:", s) }
func untrace(s string) { fmt.Println("leaving:", s) }

// Use them like this:
func a() {
    trace("a")
    defer untrace("a")
    // do something....
}
```

Мы можем сделать лучше, используя тот факт, что аргументы отложенных функций оцениваются при выполнении `defer`. Функция трассировки может установить аргумент для функции отслеживания:

```go
func trace(s string) string {
    fmt.Println("entering:", s)
    return s
}

func un(s string) {
    fmt.Println("leaving:", s)
}

func a() {
    defer un(trace("a"))
    fmt.Println("in a")
}

func b() {
    defer un(trace("b"))
    fmt.Println("in b")
    a()
}

func main() {
    b()
}
```

выводит

```
entering: b
in b
entering: a
in a
leaving: a
leaving: b
```

Для программистов, привыкших к управлению ресурсами на уровне блока в других языках, `defer` может показаться странным, но его приложения наиболее интересны именно тем, что он основан на уровне функции, а не блока. В разделах о `panic` и `recover` мы увидим ещё один пример его возможностей.

### Данные

#### Выделение памяти с помощью new

В Go есть два примитива выделения памяти: встроенные функции `new` и `make`. Они делают разные вещи и применяются к разным типам, что может сбивать с толку, но правила просты. Сначала поговорим о `new`. Это встроенная функция, которая выделяет память, но, в отличие от своих аналогов в других языках, она не *инициализирует* память, она только обнуляет её. То есть `new(T)` выделяет обнулённое пространство для новой переменной типа `T` и возвращает её адрес, значение типа `*T`. В терминологии Go это возвращает указатель на только что выделённое нулевое значение типа `T`.

Поскольку память, возвращаемая `new`, обнулена, полезно при проектировании структур данных располагать так, чтобы нулевое значение каждого типа можно было использовать без дополнительной инициализации. Это означает, что пользователь структуры данных может создать её с помощью `new` и сразу приступить к работе. Например, документация `bytes.Buffer` гласит: «Нулевое значение для `Buffer` — это пустой буфер, готовый к использованию.» Аналогично, `sync.Mutex` не имеет явного конструктора или метода `Init`. Вместо этого нулевое значение для `sync.Mutex` определяется как незаблокированный мьютекс.

Свойство «нулевое значение полезно» работает транзитивно. Рассмотрим этот тип:

```go
type SyncedBuffer struct {
    lock    sync.Mutex
    buffer  bytes.Buffer
}
```

Значения типа `SyncedBuffer` также готовы к использованию сразу после выделения или просто объявления. В следующем фрагменте и `p`, и `v` будут работать правильно без дополнительной организации:

```go
p := new(SyncedBuffer)  // type *SyncedBuffer
var v SyncedBuffer      // type  SyncedBuffer
```

#### Конструкторы и составные литералы

Иногда нулевого значения недостаточно, и необходим инициализирующий конструктор, как в этом примере, полученном из пакета `os`:

```go
func NewFile(fd int, name string) *File {
    if fd < 0 {
        return nil
    }
    f := new(File)
    f.fd = fd
    f.name = name
    f.dirinfo = nil
    f.nepipe = 0
    return f
}
```

Здесь много шаблонного кода. Мы можем упростить его, используя составной литерал, который является выражением, создающим новое значение каждый раз, когда оно вычисляется:

```go
func NewFile(fd int, name string) *File {
    if fd < 0 {
        return nil
    }
    f := File{fd, name, nil, 0}
    return &f
}
```

Обратите внимание, что, в отличие от C, вполне нормально возвращать адрес локальной переменной; хранилище, связанное с переменной, сохраняется после возврата из функции. Фактически, взятие адреса составного литерала выделяет новый экземпляр каждый раз, когда он вычисляется, поэтому мы можем объединить эти две последние строки:

```go
    return &File{fd, name, nil, 0}
```

Поля составного литерала располагаются по порядку и должны все присутствовать. Однако, помечая элементы явно как пары `field:value`, инициализаторы могут появляться в любом порядке, а отсутствующие остаются их соответствующими нулевыми значениями. Таким образом, мы можем написать

```go
    return &File{fd: fd, name: name}
```

В предельном случае, если составной литерал не содержит полей вообще, он создаёт нулевое значение для типа. Выражения `new(File)` и `&File{}` эквивалентны.

Составные литералы также можно создавать для массивов, срезов и карт, причём метки полей — это индексы или ключи карты, в зависимости от обстоятельств. В этих примерах инициализация работает независимо от значений `Enone`, `Eio` и `Einval`, если они различны:

```go
a := [...]string   {Enone: "no error", Eio: "Eio", Einval: "invalid argument"}
s := []string      {Enone: "no error", Eio: "Eio", Einval: "invalid argument"}
m := map[int]string{Enone: "no error", Eio: "Eio", Einval: "invalid argument"}
```

#### Выделение памяти с помощью make

Возвращаясь к выделению памяти. Встроенная функция `make(T, args)` служит иной цели, чем `new(T)`. Она создаёт только срезы, карты и каналы, и возвращает *инициализированное* (не обнулённое) значение типа `T` (не `*T`). Причина различия в том, что эти три типа представляют, под капотом, ссылки на структуры данных, которые должны быть инициализированы перед использованием. Например, срез — это трёхэлементный дескриптор, содержащий указатель на данные (внутри массива), длину и ёмкость, и до тех пор, пока эти элементы не инициализированы, срез равен `nil`. Для срезов, карт и каналов `make` инициализирует внутреннюю структуру данных и подготавливает значение к использованию. Например,

```go
make([]int, 10, 100)
```

выделяет массив из 100 int и создаёт структуру среза с длиной 10 и ёмкостью 100, указывающую на первые 10 элементов массива. (При создании срезов ёмкость можно опустить; см. раздел о срезах для получения дополнительной информации.) Напротив, `new([]int)` возвращает указатель на только что выделенную, обнулённую структуру среза, то есть указатель на значение `nil` среза.

Эти примеры иллюстрируют разницу между `new` и `make`:

```go
var p *[]int = new([]int)       // allocates slice structure; *p == nil; rarely useful
var v  []int = make([]int, 100) // the slice v now refers to a new array of 100 ints

// Unnecessarily complex:
var p *[]int = new([]int)
*p = make([]int, 100, 100)

// Idiomatic:
v := make([]int, 100)
```

Помните, что `make` применяется только к картам, срезам и каналам и не возвращает указатель. Чтобы получить явный указатель, выделите память с помощью `new` или возьмите адрес переменной явно.

#### Массивы

Массивы полезны при планировании детального layout памяти и иногда могут помочь избежать выделения, но в первую очередь они являются строительным блоком для срезов, которые являются предметом следующего раздела. Чтобы заложить основу для срезов, вот несколько слов о массивах.

Есть существенные различия между способами работы массивов в Go и C. В Go:

- Массивы — это значения. Присваивание одного массива другому копирует все элементы.
- В частности, если вы передаёте массив в функцию, она получит *копию* массива, а не указатель на него.
- Размер массива является частью его типа. Типы `[10]int` и `[20]int` различны.

Свойство value может быть полезным, но также и дорогим; если вы хотите поведение C и эффективность, вы можете передать указатель на массив.

```go
func Sum(a *[3]float64) (sum float64) {
    for _, v := range *a {
        sum += v
    }
    return
}

array := [...]float64{7.0, 8.5, 9.1}
x := Sum(&array)  // Note the explicit address-of operator
```

Но даже этот стиль не идиоматичен для Go. Используйте срезы вместо этого.

#### Срезы

Срезы оборачивают массивы, чтобы дать более общий, мощный и удобный интерфейс к последовательностям данных. За исключением элементов с явной размерностью (например, матрицы преобразования), большинство программирования массивов в Go выполняется с помощью срезов, а не простых массивов.

Срезы содержат ссылки на базовый массив; если вы присваиваете один срез другому, оба ссылаются на один и тот же массив. Если функция принимает аргумент-срез, изменения, которые она вносит в элементы среза, будут видны вызывающей стороне. Это аналогично передаче указателя на базовый массив. Поэтому метод чтения `Read` из пакета `os` принимает аргумент-срез, а не указатель, и вызывает его по имени; для чтения в буфер нет разницы.

Длина среза может быть изменена, пока он всё ещё помещается в пределах базового массива; просто присвойте его срезу самого себя. Ёмкость среза, доступная через встроенную функцию `cap`, сообщает максимальную длину, которую срез может принять. Вот функция для добавления данных в срез:

```go
func Append(slice, data []byte) []byte {
    l := len(slice)
    if l + len(data) > cap(slice) {  // reallocate
        // Allocate double what's needed, for future growth.
        newSlice := make([]byte, (l+len(data))*2)
        // The copy function is predeclared and works for any slice type.
        copy(newSlice, slice)
        slice = newSlice
    }
    slice = slice[0:l+len(data)]
    copy(slice[l:], data)
    return slice
}
```

Мы должны вернуть срез позже, потому что, хотя `Append` может изменить элементы `slice`, сам срез (структура данных времени выполнения, содержащая указатель, длину и ёмкость) передаётся по значению.

Идея добавления к срезу настолько полезна, что она захвачена встроенной функцией `append`. Однако, чтобы понять дизайн этой функции, нам нужно немного больше информации, поэтому мы вернёмся к ней позже.

#### Двумерные срезы

Массивы и срезы Go одномерны. Чтобы создать эквивалент двумерного массива или среза, необходимо определить массив массивов или срез срезов, например:

```go
type Transform [3][3]float64  // A 3x3 array, really an array of arrays.
type LinesOfText [][]byte     // A slice of byte slices.
```

Поскольку срезы имеют переменную длину, можно иметь каждую внутреннюю длину среза разной. Это может быть обычной ситуацией, как в нашем примере `LinesOfText`: каждая строка имеет независимую длину.

```go
text := LinesOfText{
    []byte("Now is the time"),
    []byte("for all good gophers"),
    []byte("to bring some fun to the party."),
}
```

Иногда необходимо выделить двумерный срез, например, при обработке пиксельных строк сканирования. Есть два способа достичь этого. Один — выделить каждый срез независимо; другой — выделить один массив и указать на него отдельные срезы. Какой из них использовать, зависит от вашего приложения. Если срезы могут увеличиваться или уменьшаться, они должны быть выделены независимо, чтобы избежать перезаписи следующей строки; если нет, более эффективно построить объект с одним выделением. Для справки, вот наброски двух методов. Сначала строка за строкой:

```go
// Allocate the top-level slice.
picture := make([][]uint8, YSize) // One row per unit of y.
// Loop over the rows, allocating the slice for each row.
for i := range picture {
    picture[i] = make([]uint8, XSize)
}
```

А теперь как одно выделение, нарезанное на строки:

```go
// Allocate the top-level slice, the same as before.
picture := make([][]uint8, YSize) // One row per unit of y.
// Allocate one large slice to hold all the pixels.
pixels := make([]uint8, XSize*YSize) // Has type []uint8 even though picture is [][]uint8.
// Loop over the rows, slicing each row from the front of the remaining pixels slice.
for i := range picture {
    picture[i], pixels = pixels[:XSize], pixels[XSize:]
}
```

#### Карты

Карты — удобная и мощная встроенная структура данных, связывающая значения одного типа (ключ) со значениями другого типа (элемент или значение). Ключ может быть любого типа, для которого определён оператор равенства, например, целые числа, числа с плавающей запятой и комплексные числа, строки, указатели, интерфейсы (при условии, что динамический тип поддерживает равенство), структуры и массивы. Срезы нельзя использовать в качестве ключей карт, потому что равенство для них не определено. Как и срезы, карты содержат ссылки на базовую структуру данных. Если вы передаёте карту в функцию, которая изменяет содержимое карты, изменения будут видны вызывающей стороне.

Карты можно создавать с помощью обычного синтаксиса составных литералов с парами ключ-значение, разделёнными двоеточиями, поэтому легко создавать их во время инициализации:

```go
var timeZone = map[string]int{
    "UTC":  0*60*60,
    "EST": -5*60*60,
    "CST": -6*60*60,
    "MST": -7*60*60,
    "PST": -8*60*60,
}
```

Присваивание и извлечение значений карты синтаксически выглядит так же, как и для массивов и срезов, за исключением того, что индекс не обязательно должен быть целым числом:

```go
offset := timeZone["EST"]
```

Попытка получить значение карты с ключом, которого нет в карте, вернёт нулевое значение для типа записей в карте. Например, если карта содержит целые числа, поиск несуществующего ключа вернёт `0`. Множество можно реализовать как карту со значением типа `bool`. Установка записи карты в `true` помещает значение в множество, а затем проверка его простым индексированием:

```go
attended := map[string]bool{
    "Ann": true,
    "Joe": true,
    ...
}

if attended[person] { // will be false if person is not in the map
    fmt.Println(person, "was at the meeting")
}
```

Иногда нужно отличить отсутствующую запись от нулевого значения. Есть ли запись для `"UTC"` или это `0`, потому что её вообще нет в карте? Вы можете различать с помощью формы множественного присваивания:

```go
var seconds int
var ok bool
seconds, ok = timeZone[tz]
```

По очевидным причинам это называется идиомой «запятая ok». В этом примере, если `tz` присутствует, `seconds` будет установлен соответствующим образом, а `ok` будет `true`; если нет, `seconds` будет установлен в ноль, а `ok` будет `false`. Вот функция, которая объединяет это с хорошим сообщением об ошибке:

```go
func offset(tz string) int {
    if seconds, ok := timeZone[tz]; ok {
        return seconds
    }
    log.Println("unknown time zone:", tz)
    return 0
}
```

Чтобы проверить наличие в карте, не беспокоясь о фактическом значении, вы можете использовать пустой идентификатор (`_`) вместо обычной переменной для значения:

```go
_, present := timeZone[tz]
```

Чтобы удалить запись карты, используйте встроенную функцию `delete`, аргументами которой являются карта и ключ для удаления. Это безопасно делать, даже если ключ уже отсутствует в карте.

```go
delete(timeZone, "PST")
```

#### Печать

Форматированная печать в Go использует стиль, подобный функции `printf` в C, но более богатый и общий. Функции живут в пакете `fmt` и имеют имена с заглавной буквы: `fmt.Printf`, `fmt.Fprintf`, `fmt.Sprintf` и так далее. Строковые функции (`Sprintf` и т.д.) возвращают строку, а не заполняют предоставленный буфер.

Вам не нужно предоставлять строку формата. Для каждой из `Printf`, `Fprintf` и `Sprintf` есть другая пара функций, например, `Print` и `Println`. Эти функции не принимают строку формата, но генерируют формат по умолчанию для каждого аргумента. Версии `Println` добавляют пробелы между аргументами и новую строку в выводе, в то время как версии `Print` добавляют пробелы только между операндами, если операнд с обеих сторон не является строкой. В этом примере каждая строка даёт одинаковый результат:

```go
fmt.Printf("Hello %d\n", 23)
fmt.Fprint(os.Stdout, "Hello ", 23, "\n")
fmt.Println("Hello", 23)
fmt.Println(fmt.Sprint("Hello ", 23))
```

Функции форматированной печати `fmt.Fprint` и друзья принимают в качестве первого аргумента любой объект, реализующий интерфейс `io.Writer`; переменные `os.Stdout` и `os.Stderr` — знакомые примеры.

Здесь всё начинает отличаться от C. Во-первых, числовые форматы, такие как `%d`, не принимают флаги знака или размера; вместо этого подпрограммы печати используют тип аргумента для решения этих свойств.

```go
var x uint64 = 1<<64 - 1
fmt.Printf("%d %x; %d %x\n", x, x, int64(x), int64(x))
```

печатает

```
18446744073709551615 ffffffffffffffff; -1 -1
```

Если вы просто хотите преобразование по умолчанию, такое как десятичное для целых чисел, вы можете использовать универсальный формат `%v` (для «значения»); результат точно такой же, как `Print` и `Println` произвели бы. Более того, этот формат может печатать *что угодно*, даже массивы, срезы, структуры и карты. Вот оператор печати для карты часовых поясов, определённой в предыдущем разделе:

```go
fmt.Printf("%v\n", timeZone)  // or just fmt.Println(timeZone)
```

который даёт вывод

```
map[CST:-21600 EST:-18000 MST:-25200 PST:-28800 UTC:0]
```

Для карт `Printf` и друзья сортируют вывод лексикографически по ключу.

При печати структуры модифицированный формат `%+v` аннотирует каждое поле структуры его именем, а для любого значения альтернативный формат `%#v` печатает значение в полном синтаксисе Go.

```go
type T struct {
    a int
    b float64
    c string
}
t := &T{ 7, -2.35, "abc\tdef" }
fmt.Printf("%v\n", t)
fmt.Printf("%+v\n", t)
fmt.Printf("%#v\n", t)
fmt.Printf("%#v\n", timeZone)
```

печатает

```
&{7 -2.35 abc   def}
&{a:7 b:-2.35 c:abc     def}
&main.T{a:7, b:-2.35, c:"abc\tdef"}
map[string]int{"CST":-21600, "EST":-18000, "MST":-25200, "PST":-28800, "UTC":0}
```

(Обратите внимание на амперсанды.) Этот формат в кавычках также доступен при применении к значениям типа `string` или `[]byte` через `%q`; он выдаёт строку в кавычках. Альтернативный формат `%#q` будет использовать обратные кавычки, если это возможно. (`%q` также работает для целых чисел и рун, создавая односимвольный литерал в кавычках.) Также `%x` работает для строк, байтовых массивов и байтовых срезов, а также для целых чисел, генерируя длинную шестнадцатеричную строку. С пробелом в формате (`% x`) он помещает пробелы между байтами.

Другой удобный формат — `%T`, который печатает *тип* значения.

```go
fmt.Printf("%T\n", timeZone)
```

печатает

```
map[string]int
```

Если вы хотите контролировать формат по умолчанию для пользовательского типа, всё, что вам нужно сделать, — это определить метод с сигнатурой `String() string` для типа. Для нашего простого типа `T` это может выглядеть так:

```go
func (t *T) String() string {
    return fmt.Sprintf("%d/%g/%q", t.a, t.b, t.c)
}
fmt.Printf("%v\n", t)
```

чтобы напечатать в формате

```
7/-2.35/"abc\tdef"
```

(Если вам нужно печатать значения типа `T`, а также указатели на `T`, получатель для `String` должен быть типа значения; этот пример использовал указатель, потому что это более эффективно и идиоматично для типов структур. См. раздел ниже о получателях указателей и значений для получения дополнительной информации.)

Наш метод `String` может вызывать `Sprintf`, потому что подпрограммы печати полностью реентерабельны и могут быть обёрнуты таким образом. Однако есть важная деталь, которую нужно понять о таком подходе: не создавайте метод `String`, вызывая `Sprintf` таким образом, чтобы он рекурсивно вызывал ваш метод `String`. Это может произойти, если вызов `Sprintf` пытается напечатать получателя напрямую как строку, что, в свою очередь, вызовет метод снова. Это распространённая ошибка, как показано в этом примере:

```go
type MyString string
func (m MyString) String() string {
    return fmt.Sprintf("MyString=%s", m) // Error: will recur forever.
}
```

Это также легко исправить: преобразуйте аргумент в базовый строковый тип, который не имеет метода:

```go
type MyString string
func (m MyString) String() string {
    return fmt.Sprintf("MyString=%s", string(m)) // OK: note conversion.
}
```

В разделе об инициализации мы увидим ещё одну технику, которая избегает этой рекурсии.

Другой метод печати — передать аргументы подпрограммы печати другой такой подпрограмме. Сигнатура `Printf` использует тип `...interface{}` для своего последнего аргумента, чтобы после формата могло появиться произвольное количество параметров любого типа.

```go
func Printf(format string, v ...interface{}) (n int, err error) {
```

Внутри функции `Printf` `v` действует как переменная типа `[]interface{}`, но если она передаётся другой вариативной функции, она распаковывается как обычный список аргументов. Вот реализация функции `log.Println`, которую мы использовали выше. Она передаёт свои аргументы непосредственно в `fmt.Sprintln` для фактического форматирования.

```go
// Println prints to the standard logger in the manner of fmt.Println.
func Println(v ...interface{}) {
    std.Output(2, fmt.Sprintln(v...))  // Output takes parameters (int, string)
}
```

Мы пишем `...` после `v` в вложенном вызове `Sprintln`, чтобы сообщить компилятору рассматривать `v` как список аргументов; в противном случае он передал бы `v` как единственный аргумент среза.

Есть ещё много возможностей печати, о которых мы не говорили. Смотрите документацию `godoc` для пакета `fmt` для деталей.

Кстати, вариативный параметр может быть конкретного типа, например, `...int` для функции min, которая выбирает наименьшее целое число из списка:

```go
// Min returns the smallest of the integers in its argument list.
func Min(a ...int) int {
    min := int(^uint(0) >> 1)  // largest int
    for _, i := range a {
        if i < min {
            min = i
        }
    }
    return min
}
```

#### Append

Теперь у нас есть недостающие части, необходимые для объяснения дизайна встроенной функции `append`. Подпись `append` отличается от нашей пользовательской функции `Append` выше. Схематично это так:

```go
func append(slice []T, elements ...T) []T
```

где `T` — заполнитель для любого заданного типа. Вы не можете фактически написать функцию в Go, где тип `T` определяется вызывающей стороной. Именно поэтому `append` встроена: она требует поддержки компилятора.

То, что делает `append`, — добавляет элементы в конец среза и возвращает результат. Результат должен быть возвращён, потому что, как и в нашем рукописном `Append`, базовый массив может измениться. В этом простом примере

```go
x := []int{1,2,3}
x = append(x, 4, 5, 6)
fmt.Println(x)
```

печатается `[1 2 3 4 5 6]`. Поэтому `append` работает как `Printf`, собирая произвольное количество аргументов.

Но что, если мы хотим сделать то, что делает наш `Append`, и добавить срез к срезу? Легко: используйте `...` во время вызова, так же, как мы это делали в выводе выше. Этот фрагмент даёт тот же результат, что и предыдущий:

```go
x := []int{1,2,3}
y := []int{4,5,6}
x = append(x, y...)
fmt.Println(x)
```

Без этих `...` он бы не скомпилировался, потому что типы были бы неправильными; `y` не типа `int`.

### Инициализация

Хотя это выглядит не сильно отличающимся от C или C++ на первый взгляд, инициализация в Go более мощная. Во время инициализации можно создавать сложные структуры, и порядок инициализации между инициализированными объектами, даже разными пакетами, обрабатывается правильно.

#### Константы

Константы в Go — это просто константы. Они создаются во время компиляции, даже когда определены как локальные переменные внутри функций, и могут быть только числами, символами (рунами), строками или логическими значениями. Из-за ограничения времени компиляции выражения, определяющие их, должны быть константными выражениями, вычислимыми компилятором. Например, `1<<3` — константное выражение, а `math.Sin(math.Pi/4)` — нет, потому что вызов функции `math.Sin` должен произойти во время выполнения.

В Go перечисляемые константы создаются с помощью `iota`. Поскольку `iota` может быть частью выражения и выражения могут быть неявно повторены, легко создавать сложные наборы значений.

```go
type ByteSize float64

const (
    _           = iota // ignore first value by assigning to blank identifier
    KB ByteSize = 1 << (10 * iota)
    MB
    GB
    TB
    PB
    EB
    ZB
    YB
)
```

Возможность прикреплять метод, такой как `String`, к любому пользовательскому типу позволяет таким значениям автоматически форматироваться для печати. Хотя вы увидите это чаще всего применяемым к структурам, эта техника также полезна для скалярных типов, таких как целочисленный тип с плавающей запятой, такой как `ByteSize`.

```go
func (b ByteSize) String() string {
    switch {
    case b >= YB:
        return fmt.Sprintf("%.2fYB", b/YB)
    case b >= ZB:
        return fmt.Sprintf("%.2fZB", b/ZB)
    case b >= EB:
        return fmt.Sprintf("%.2fEB", b/EB)
    case b >= PB:
        return fmt.Sprintf("%.2fPB", b/PB)
    case b >= TB:
        return fmt.Sprintf("%.2fTB", b/TB)
    case b >= GB:
        return fmt.Sprintf("%.2fGB", b/GB)
    case b >= MB:
        return fmt.Sprintf("%.2fMB", b/MB)
    case b >= KB:
        return fmt.Sprintf("%.2fKB", b/KB)
    }
    return fmt.Sprintf("%.2fB", b)
}
```

Выражение `YB` печатает как `1.00YB`, а `ByteSize(1e13)` печатает как `9.09TB`.

Использование здесь `Sprintf` для реализации `ByteSize` `String` безопасно (не вызывает бесконечной рекурсии), потому что `Sprintf` вызывает `%f`, который не является строковым форматом: `Sprintf` будет вызывать метод `String` только тогда, когда ему нужна строка, а `%f` хочет значение с плавающей запятой.

#### Переменные

Переменные можно инициализировать как константы, но инициализатором может быть общее выражение, вычисляемое во время выполнения.

```go
var (
    home   = os.Getenv("HOME")
    user   = os.Getenv("USER")
    gopath = os.Getenv("GOPATH")
)
```

#### Функция init

Наконец, каждый исходный файл может определять свою собственную функцию `init` без аргументов для настройки любого состояния, которое необходимо. (Фактически, каждый файл может иметь несколько функций `init`.) И `init` вызывается после того, как все объявления переменных в пакете получили свои начальные значения, и они оцениваются после инициализации всех импортированных пакетов.

Помимо инициализации, которую нельзя выразить как объявление, распространённым применением функций `init` является проверка или исправление состояния программы перед началом реального выполнения.

```go
func init() {
    if user == "" {
        log.Fatal("$USER not set")
    }
    if home == "" {
        home = "/home/" + user
    }
    if gopath == "" {
        gopath = home + "/go"
    }
    // gopath may be overridden by --gopath flag on command line.
    flag.StringVar(&gopath, "gopath", gopath, "override default GOPATH")
}
```

### Методы

#### Указатели против значений

Как мы видели в примерах `ByteSize`, методы могут быть определены для любого именованного типа (кроме указателя или интерфейса); получатель не обязательно должен быть структурой.

В обсуждении срезов выше мы написали функцию `Append`. Мы могли бы определить её как метод для срезов вместо этого. Для этого мы сначала объявляем именованный тип, к которому можем привязать метод, а затем делаем получателя метода экземпляром этого типа.

```go
type ByteSlice []byte

func (slice ByteSlice) Append(data []byte) []byte {
    // Body exactly the same as the Append function defined above.
}
```

Это всё ещё требует, чтобы метод возвращал обновлённый срез. Мы можем устранить эту неуклюжесть, взяв *указатель* на `ByteSlice` в качестве получателя, чтобы метод мог перезаписать срез вызывающей стороны.

```go
func (p *ByteSlice) Append(data []byte) {
    slice := *p
    // Body as above, without the return.
    *p = slice
}
```

Фактически, мы можем сделать даже лучше. Если мы модифицируем нашу функцию так, чтобы она выглядела как стандартный метод `Write`, вот так,

```go
func (p *ByteSlice) Write(data []byte) (n int, err error) {
    slice := *p
    // Again as above.
    *p = slice
    return len(data), nil
}
```

тогда тип `*ByteSlice` удовлетворяет стандартному интерфейсу `io.Writer`, что удобно. Например, мы можем напечатать в него:

```go
    var b ByteSlice
    fmt.Fprintf(&b, "This hour has %d days\n", 7)
```

Мы передаём адрес `ByteSlice`, потому что только `*ByteSlice` удовлетворяет `io.Writer`. Правило о получателях указателей против значений таково: методы значений могут вызываться как для указателей, так и для значений, но методы указателей могут вызываться только для указателей.

Это правило возникает потому, что методы указателей могут изменять получателя; вызов их для значения привёл бы к тому, что метод получил бы копию значения, и любые изменения были бы отброшены. Поэтому язык запрещает эту ошибку. Однако есть удобное исключение: когда значение адресуемо, язык автоматически заботится о взятии адреса при вызове метода указателя на значение. В нашем примере переменная `b` адресуема, поэтому мы можем вызвать её метод `Write` просто как `b.Write`. Компилятор перепишет его на `(&b).Write` для нас.

Кстати, идея использования `Write` на срезе байтов центральна для реализации `bytes.Buffer`.

### Интерфейсы и другие типы

#### Интерфейсы

Интерфейсы в Go предоставляют способ указать поведение объекта: если что-то может делать *это*, то его можно использовать *здесь*. Мы уже видели пару простых примеров; пользовательские принтеры могут быть реализованы методом `String`, в то время как `Fprintf` может генерировать вывод для чего угодно, что реализует `Write`. Интерфейсы с одним или двумя методами распространены в коде Go и обычно дают имя, производное от метода, как в `io.Writer` для чего-то, что реализует `Write`.

Типы могут реализовывать несколько интерфейсов. Например, коллекции могут быть отсортированы функциями в пакете `sort`, если они реализуют `sort.Interface`, который содержит `Len()`, `Less(i, j int) bool` и `Swap(i, j int)`, а также могут иметь собственный формат принтера. В искусственном примере в пакете `sort` есть

```go
type Sequence []int

// Methods required by sort.Interface.
func (s Sequence) Len() int {
    return len(s)
}
func (s Sequence) Less(i, j int) bool {
    return s[i] < s[j]
}
func (s Sequence) Swap(i, j int) {
    s[i], s[j] = s[j], s[i]
}

// Copy returns a copy of the Sequence.
func (s Sequence) Copy() Sequence {
    copy := make(Sequence, 0, len(s))
    return append(copy, s...)
}

// Method for printing - sorts the elements before printing.
func (s Sequence) String() string {
    s = s.Copy() // Make a copy; don't overwrite argument.
    sort.Sort(s)
    str := "["
    for i, elem := range s { // Loop is O(N²); will fix that in next example.
        if i > 0 {
            str += " "
        }
        str += fmt.Sprint(elem)
    }
    return str + "]"
}
```

#### Преобразования

Метод `String` из `Sequence` повторно выполняет работу, которую уже выполняет `Sprint` для срезов. (Он также имеет сложность O(N²), что плохо.) Если мы вызовем `Sprint` на `Sequence` перед его сортировкой, мы сможем извлечь выгоду из работы, которую `Sprint` уже делает для нас.

```go
func (s Sequence) String() string {
    s = s.Copy()
    sort.Sort(s)
    return fmt.Sprint([]int(s))
}
```

Этот метод — ещё один пример техники преобразования для вызова `String` безопасно, потому что если мы игнорируем имя типа, `Sequence` и `[]int` совпадают, и поэтому допустимо преобразовывать между ними. Преобразование не создаёт копию, оно просто временно имеет новое представление значения.

Идиоматично в программах на Go преобразовывать тип выражения для доступа к другому набору методов. В качестве примера можно использовать существующий тип `sort.IntSlice`, чтобы уменьшить весь пример до этого:

```go
type Sequence []int

// Method for printing - sorts the elements before printing
func (s Sequence) String() string {
    s = s.Copy()
    sort.IntSlice(s).Sort()
    return fmt.Sprint([]int(s))
}
```

Теперь, вместо того чтобы заставлять `Sequence` реализовывать несколько интерфейсов (сортировку и печать), мы используем возможность преобразования элемента данных в несколько типов (`Sequence`, `sort.IntSlice` и `[]int`), каждый из которых выполняет часть работы. Это более необычно на практике, но может быть эффективно.

#### Преобразования интерфейсов и утверждения типа

`Type switch` — это форма преобразования: она принимает интерфейс и, для каждого случая, эффективно преобразует его в тип этого случая. Вот упрощённая версия кода из `fmt.Printf` под капотом, которая преобразует значение в строку, используя проверку типа. Если это уже строка, мы хотим фактическое строковое значение, содержащееся внутри, а если она имеет метод `String`, мы хотим результат вызова метода.

```go
type Stringer interface {
    String() string
}

var value interface{} // Value provided by caller.
switch str := value.(type) {
case string:
    return str
case Stringer:
    return str.String()
}
```

Первый случай находит конкретное значение; второй преобразует интерфейс в другой интерфейс. Это совершенно нормально смешивать типы таким образом.

Что, если есть только один тип, который нас интересует? Если мы знаем, что значение содержит строку, и мы просто хотим её извлечь? Одноэлементный type switch подойдёт, но также подойдёт type assertion. Type assertion принимает значение интерфейса и извлекает из него значение указанного явного типа.

```go
value.(typeName)
```

и результатом является новое значение со статическим типом `typeName`. Этот тип должен быть либо конкретным типом, который содержит интерфейс, либо вторым интерфейсным типом, в который значение может быть преобразовано. Чтобы извлечь строку, которую, как мы знаем, содержит значение, мы могли бы написать:

```go
str := value.(string)
```

Но если окажется, что значение не содержит строку, программа завершится с ошибкой во время выполнения. Чтобы защититься от этого, используйте идиому «запятая ok» для безопасной проверки того, является ли значение строкой:

```go
str, ok := value.(string)
if ok {
    fmt.Printf("string value is: %q\n", str)
} else {
    fmt.Printf("value is not a string\n")
}
```

Если утверждение типа не сработает, `str` всё равно будет существовать и будет строкой, нулевой строкой.

В качестве иллюстрации возможностей вот оператор `if-else`, эквивалентный type switch, который открыл этот раздел.

```go
if str, ok := value.(string); ok {
    return str
} else if str, ok := value.(Stringer); ok {
    return str.String()
}
```

#### Общность

Если тип существует только для реализации интерфейса и никогда не будет иметь экспортируемых методов, кроме этого интерфейса, нет необходимости экспортировать сам тип. Экспорт только интерфейса даёт понять, что значение не имеет интересного поведения, кроме описанного в интерфейсе. Это также избегает необходимости повторять документацию для каждого экземпляра общего метода.

В таких случаях конструктор должен возвращать значение интерфейса, а не реализующий тип. Например, в библиотеках хеширования `crc32.NewIEEE` и `adler32.New` оба возвращают интерфейсный тип `hash.Hash32`. Замена алгоритма CRC-32 на Adler-32 в программе на Go требует только изменения вызова конструктора; остальной код не зависит от различий между алгоритмами.

Аналогичный подход позволяет алгоритмам потокового шифрования, в разных пакетах `crypto`, быть отделёнными от блочных шифров, которые они связывают вместе. Интерфейс `Block` в пакете `crypto/cipher` определяет поведение блочного шифра, который обеспечивает шифрование одного блока данных. Затем, по аналогии с пакетом `bufio`, пакеты шифрования, которые реализуют этот интерфейс, могут использоваться для создания потоковых шифров, представленных интерфейсом `Stream`, без знания деталей блочного шифрования. Интерфейсы `crypto/cipher` выглядят так:

```go
type Block interface {
    BlockSize() int
    Encrypt(dst, src []byte)
    Decrypt(dst, src []byte)
}

type Stream interface {
    XORKeyStream(dst, src []byte)
}
```

Вот определение режима счётчика (CTR), который превращает блочный шифр в потоковый шифр; обратите внимание, что детали блочного шифра абстрагированы:

```go
// NewCTR returns a Stream that encrypts/decrypts using the given Block in
// counter mode. The length of iv must be the same as the Block's block size.
func NewCTR(block Block, iv []byte) Stream
```

`NewCTR` применяется не только к одному конкретному алгоритму шифрования и источнику данных, но к любой реализации интерфейсов `Block` и `Stream`. Поскольку они возвращают интерфейсные значения, замена шифрования CTR другими режимами шифрования является локальным изменением. Вызовы конструктора должны быть отредактированы, но окружающий код, из-за того, что он должен обрабатывать результат только как `Stream`, не должен заметить разницы.

#### Интерфейсы и методы

Поскольку почти всё можно прикрепить методы к почти всему, возникает соблазн определить методы для всех случаев. Для интерфейсов это возможно, но обычно не нужно.

Интерфейсы — это способ указания поведения объекта, а не того, чем он является или что содержит. Мы уже видели пару простых примеров. Интерфейсы, как правило, содержат небольшое количество методов, часто один или два. Go не имеет автоматически удовлетворяемых интерфейсов на основе совпадения имён. Это позволяет избежать проблем, которые могут возникнуть, когда сигнатура интерфейса изменяется.

Например, тип, реализующий `String`, может также реализовать `Format`, но это не обязательно; и наоборот, тип, реализующий `Format`, не обязан реализовывать `String`.

Интерфейсы с несколькими методами обычно требуют больше кода. Например, `sort.Interface` требует `Len`, `Less` и `Swap`, но `sort` также имеет обёртки для работы с `[]int`, `[]string` и т.д.

Иногда компромисс стоит того. Но не определяйте методы для всех случаев: используйте интерфейсы только тогда, когда они действительно нужны.

### Встроенные (embedded) типы

Go не предоставляет типичного, управляемого типами, подкласса. Но он имеет возможность «заимствовать» части реализации, встраивая типы в структуры или интерфейсы.

Встраивание интерфейса очень просто. Мы уже упоминали интерфейсы `io.Reader` и `io.Writer` ранее; вот их определения:

```go
type Reader interface {
    Read(p []byte) (n int, err error)
}

type Writer interface {
    Write(p []byte) (n int, err error)
}
```

Пакет `io` также экспортирует несколько других интерфейсов, которые определяют объекты, которые могут реализовывать один или несколько таких методов. Например, есть `io.ReadWriter`, интерфейс, содержащий оба метода `Read` и `Write`. Мы могли бы указать `io.ReadWriter` явно, перечислив два метода, но проще и более вызывающе — встроить два интерфейса для создания нового, например:

```go
// ReadWriter is the interface that combines the Reader and Writer interfaces.
type ReadWriter interface {
    Reader
    Writer
}
```

Это говорит то, что кажется: `ReadWriter` может делать всё, что может `Reader`, и всё, что может `Writer`; это объединение встроенных интерфейсов. Только интерфейсы могут быть встроены в интерфейсы.

Та же основная идея применяется к структурам, но с более далеко идущими последствиями. Интерфейс `bufio.ReadWriter` в пакете `bufio`:

```go
// ReadWriter stores pointers to a Reader and a Writer.
// It implements io.ReadWriter.
type ReadWriter struct {
    *Reader  // *bufio.Reader
    *Writer  // *bufio.Writer
}
```

Встроенные элементы — это указатели на структуры и, конечно, должны быть инициализированы, чтобы указывать на допустимые структуры, прежде чем их можно будет использовать. Структура `ReadWriter` может быть записана как

```go
type ReadWriter struct {
    reader *Reader
    writer *Writer
}
```

но тогда для продвижения полей и удовлетворения интерфейса `io` нам также понадобились бы методы перенаправления, такие как:

```go
func (rw *ReadWriter) Read(p []byte) (n int, err error) {
    return rw.reader.Read(p)
}
```

Встраивая структуры напрямую, мы избегаем этой бухгалтерии. Метод встроенного типа приходит бесплатно, что означает, что `bufio.ReadWriter` не только имеет методы `bufio.Reader` и `bufio.Writer`, но также удовлетворяет всем трём интерфейсам: `io.Reader`, `io.Writer` и `io.ReadWriter`.

Есть важное отличие встраивания от подклассов. Когда мы встраиваем тип, методы этого типа становятся методами внешнего типа, но когда метод вызывается, получателем метода является внутренний тип, а не внешний. В нашем примере, когда метод `Read` для `bufio.ReadWriter` вызывается, он имеет тот же эффект, что и метод перенаправления, написанный выше; получателем является `reader` поля `ReadWriter`, а не сам `ReadWriter`.

Встраивание также может быть просто удобством. Этот пример показывает встроенное поле рядом с обычным именованным полем.

```go
type Job struct {
    Command string
    *log.Logger
}
```

Теперь тип `Job` имеет методы `Print`, `Printf`, `Println` и другие из `*log.Logger`. Мы могли бы дать ему имя поля, конечно, но в этом нет необходимости. И теперь, после инициализации, мы можем логировать в `Job`:

```go
job.Println("starting now...")
```

`Logger` — это обычное поле структуры `Job`, поэтому мы можем инициализировать его обычным способом в конструкторе для `Job`, например:

```go
func NewJob(command string, logger *log.Logger) *Job {
    return &Job{command, logger}
}
```

или с помощью составного литерала:

```go
job := &Job{command, log.New(os.Stderr, "Job: ", log.Ldate)}
```

Если нам нужно обратиться к встроенному полю напрямую, имя типа поля, игнорируя квалификатор пакета, действует как имя поля, как в этом примере, если бы нам нужно было получить доступ к полю `*log.Logger` переменной `Job` с именем `job`. Здесь нам нужен доступ к `job.Logger`, что полезно, если мы хотим уточнить методы `Logger`.

```go
func (job *Job) Printf(format string, args ...interface{}) {
    job.Logger.Printf("%q: %s", job.Command, fmt.Sprintf(format, args...))
}
```

Встраивание типов вводит проблему конфликтов имён, но правила для их разрешения просты. Во-первых, поле или метод `X` скрывает любой другой элемент `X` на более глубоком уровне вложенности. Если `log.Logger` содержал поле или метод с именем `Command`, поле `Command` из `Job` было бы доминирующим.

Во-вторых, если одно и то же имя появляется на одном уровне вложенности, обычно это ошибка; было бы ошибкой встраивать `log.Logger`, если бы другое поле или метод `Logger` также присутствовали. Однако, если дублирующее имя никогда не упоминается в программе вне самого типа, ошибки нет. Это правило даёт некоторую защиту от изменений типов, встроенных извне; нет проблем, если добавляется поле, которое конфликтует с другим подполем, если ни одно из них никогда не используется.

### Согласованность (concurrency)

#### Разделяемая память через коммуникацию

Согласованное программирование — большая тема, и здесь есть место только для некоторых специфичных для Go моментов.

Согласованное программирование во многих средах затруднено из-за требования корректного доступа к разделяемой памяти. Go поощряет другой подход, в котором разделяемые значения передаются по каналам и фактически никогда активно не разделяются отдельными потоками выполнения. В любой момент времени только одна горутина имеет доступ к значению. Гонки данных не могут происходить по конструкции. Чтобы поощрить этот образ мышления, мы свели его к слогану:

> Не общайтесь, разделяя память; вместо этого разделяйте память, общаясь.

Этот подход может быть завышенным. Подсчёт ссылок лучше всего делать с помощью мьютекса, окружающего целочисленную переменную. Но как высокоуровневый подход, использование каналов для управления доступом облегчает написание ясных, правильных программ.

Один из способов думать об этой модели — рассмотреть типичный однопоточный запуск программы на одном процессоре. Нет необходимости в синхронизации примитивов. Теперь запустите другой такой экземпляр; ему также не нужна синхронизация. Теперь позвольте этим двум взаимодействовать; если взаимодействие — это синхронизация, то всё ещё не нужны другие примитивы синхронизации. Например, Unix-конвейеры идеально вписываются в эту модель. Хотя согласованность в Go не является Unix-конвейерами, по духу она похожа, и подход может быть успешным, поскольку он прост.

#### Горутины

Они называются *goroutines*, потому что существующие термины — потоки, сопрограммы, процессы и т.д. — передают неточные коннотации. Горутина имеет простую модель: это функция, выполняющаяся одновременно с другими горутинами в том же адресном пространстве. Она лёгкая, стоит чуть больше, чем выделение пространства стека. И стеки начинаются маленькими, поэтому они дешёвы, и растут, выделяя (и освобождая) кучную память по мере необходимости.

Горутины мультиплексируются на несколько потоков ОС, поэтому, если одна блокируется, например, при ожидании I/O, другие продолжают работать. Их дизайн скрывает много сложности создания потоков и управления ими.

Префикс `go` у вызова функции запускает новую горутину. Когда вызов завершается, горутина молча завершается. (Эффект похож на команду `&` в оболочке Unix.)

```go
go list.Sort()  // run list.Sort concurrently; don't wait for it.
```

Функциональный литерал может быть удобен в вызове `go`.

```go
func Announce(message string, delay time.Duration) {
    go func() {
        time.Sleep(delay)
        fmt.Println(message)
    }()  // Note the parentheses - must call the function.
}
```

В Go функциональные литералы — это замыкания: реализация гарантирует, что переменные, на которые ссылается функция, сохраняются до тех пор, пока они активны.

Эти примеры не очень практичны, потому что функции не имеют способа сигнализировать о завершении. Для этого нам нужны каналы.

#### Каналы

Как и карты, каналы выделяются с помощью `make`, и результирующее значение действует как ссылка на базовую структуру данных. Если необязательный целочисленный параметр указан, он устанавливает размер буфера для канала. По умолчанию значение равно нулю, для небуферизованного или синхронного канала.

```go
ci := make(chan int)            // unbuffered channel of integers
cj := make(chan int, 0)         // unbuffered channel of integers
cs := make(chan *os.File, 100)  // buffered channel of pointers to Files
```

Небуферизованные каналы объединяют коммуникацию с синхронизацией — обмен гарантирует, что две горутины (используя слово в его обычном значении) находятся в известном состоянии.

Есть много хороших идиом использования каналов. Вот одна, с которой мы начали. В предыдущем разделе мы запускали сортировку в фоне. Канал может позволить запускающей горутине ждать завершения сортировки.

```go
c := make(chan int)  // Allocate a channel.
// Start the sort in a goroutine; when it completes, signal on the channel.
go func() {
    list.Sort()
    c <- 1  // Send a signal; value does not matter.
}()
doSomethingForAWhile()
<-c   // Wait for sort to finish; discard sent value.
```

Получатели всегда блокируются, пока не появятся данные для получения. Если канал небуферизован, отправитель блокируется, пока получатель не получит значение. Если канал имеет буфер, отправитель блокируется только до тех пор, пока значение не будет скопировано в буфер; если буфер заполнен, это означает ожидание, пока какой-нибудь получатель не извлечёт значение.

Буферизованный канал можно использовать как семафор, например, для ограничения пропускной способности. В этом примере входящие запросы передаются в `handle`, который отправляет значение в канал, обрабатывает запрос и получает значение из канала, чтобы подготовить «семафор» для следующего потребителя. Ёмкость буфера канала ограничивает количество одновременных вызовов `process`.

```go
var sem = make(chan int, MaxOutstanding)

func handle(r *Request) {
    sem <- 1    // Wait for active queue to drain.
    process(r)  // May take a long time.
    <-sem       // Done; enable next request to run.
}

func Serve(queue chan *Request) {
    for {
        req := <-queue
        go handle(req)  // Don't wait for handle to finish.
    }
}
```

Как только `MaxOutstanding` обработчиков выполняют `process`, больше не будет приниматься ни один входящий запрос, пока один из них не завершится и не освободит место в буфере канала.

Однако этот дизайн имеет проблему: `Serve` создаёт новую горутину для каждого входящего запроса, даже если только `MaxOutstanding` из них могут выполняться в любой момент времени. В результате, если запросы поступают слишком быстро, программа может потреблять неограниченные ресурсы. Мы можем исправить этот недостаток, изменив `Serve` на управление созданием горутин через тот же буферный канал. Это также устраняет вызов `go` из `handle`, поскольку теперь количество запущенных горутин ограничено.

```go
func Serve(queue chan *Request) {
    for req := range queue {
        sem <- 1
        go func() {
            process(req) // Buggy; see explanation below.
            <-sem
        }()
    }
}
```

Вот важная деталь: в этом коде есть ошибка. Переменная `req` разделяется между всеми горутинами, поэтому `req` будет меняться во время выполнения горутин. Вам нужно убедиться, что `req` уникальна для каждой горутины. Вот один из способов сделать это — передать значение `req` в качестве аргумента в замыкание:

```go
func Serve(queue chan *Request) {
    for req := range queue {
        sem <- 1
        go func(req *Request) {
            process(req)
            <-sem
        }(req)
    }
}
```

Сравните эту версию с предыдущей, чтобы увидеть, как изменилось объявление и запуск замыкания. Другое решение — создать переменную с тем же именем, как в этом примере:

```go
func Serve(queue chan *Request) {
    for req := range queue {
        req := req // Create new instance of req for the goroutine.
        sem <- 1
        go func() {
            process(req)
            <-sem
        }()
    }
}
```

Может показаться странным писать

```go
req := req
```

но это законно и идиоматично в Go. Вы получаете новую версию переменной с тем же именем, намеренно затеняя переменную цикла локально, но делая её уникальной для каждой горутины.

Возвращаясь к общей проблеме написания сервера, другой подход, который хорошо управляет ресурсами, — запустить фиксированное количество горутин `handle`, все читающие из канала запросов. Количество горутин ограничивает количество одновременных вызовов `process`. Эта функция `Serve` также принимает канал, который ей говорят закрыть; после запуска горутин она блокируется на получение из этого канала.

```go
func handle(queue chan *Request) {
    for r := range queue {
        process(r)
    }
}

func Serve(clientRequests chan *Request, quit chan bool) {
    // Start handlers
    for i := 0; i < MaxOutstanding; i++ {
        go handle(clientRequests)
    }
    <-quit  // Wait to be told to exit.
}
```

#### Каналы каналов

Одна из наиболее важных особенностей Go заключается в том, что каналы являются первоклассными значениями и могут быть выделены и переданы как любой другой. Обычное использование этого свойства — реализовать безопасный, параллельный диспетчер запросов.

В примере в предыдущем разделе `handle` был идеализированным обработчиком, но мы не определили тип запроса, который он обрабатывает. Если этот тип включает канал для ответа, каждый клиент может предоставить свой собственный путь для ответа. Вот схематичное определение типа `Request`:

```go
type Request struct {
    args        []int
    f           func([]int) int
    resultChan  chan int
}
```

Клиент предоставляет функцию и её аргументы, а также канал внутри объекта запроса, по которому можно получить ответ.

```go
func sum(a []int) (s int) {
    for _, v := range a {
        s += v
    }
    return
}

request := &Request{[]int{3, 4, 5}, sum, make(chan int)}
// Send request
clientRequests <- request
// Wait for response.
fmt.Printf("answer: %d\n", <-request.resultChan)
```

На стороне сервера функция-обработчик — это единственное, что меняется:

```go
func handle(queue chan *Request) {
    for req := range queue {
        req.resultChan <- req.f(req.args)
    }
}
```

Очевидно, что нужно сделать гораздо больше, чтобы сделать это реалистичным, но этот код является основой для параллельной, ограниченной по скорости, неблокирующей системы RPC, и в нём нет мьютекса в поле зрения.

#### Параллелизация

Ещё одно применение этих идей — распараллелить вычисление на нескольких ядрах CPU. Если вычисление можно разбить на отдельные части, которые выполняются независимо, его можно распараллелить, используя канал для сигнализации о завершении каждой части.

Допустим, у нас есть дорогостоящая операция над вектором целых чисел, и значение каждой записи независимо от других, как в этом идеализированном примере:

```go
type Vector []float64

// Apply the operation to v[i], v[i+1] ... up to v[n-1].
func (v Vector) DoSome(i, n int, u Vector, c chan int) {
    for ; i < n; i++ {
        v[i] += u.Op(v[i])
    }
    c <- 1    // signal that this piece is done
}
```

Мы запускаем части независимо в цикле, по одной горутине на ядро CPU. Они могут завершиться в любом порядке, но это неважно; мы просто подсчитываем сигналы завершения, опустошая канал после запуска всех горутин.

```go
const numCPU = 4 // number of CPU cores

func (v Vector) DoAll(u Vector) {
    c := make(chan int, numCPU)  // Buffering optional but sensible.
    for i := 0; i < numCPU; i++ {
        go v.DoSome(i*len(v)/numCPU, (i+1)*len(v)/numCPU, u, c)
    }
    // Drain the channel.
    for i := 0; i < numCPU; i++ {
        <-c    // wait for one task to complete
    }
    // All done.
}
```

Вместо создания постоянного значения для `numCPU` мы можем запросить у среды выполнения подходящее значение. Функция `runtime.NumCPU` возвращает количество ядер CPU на машине, поэтому мы могли бы написать

```go
var numCPU = runtime.NumCPU()
```

Также есть функция `runtime.GOMAXPROCS`, которая сообщает (или устанавливает) пользовательское значение ресурса ядра CPU, которое программа может использовать одновременно. По умолчанию `runtime.GOMAXPROCS(runtime.NumCPU())`, но программы могут изменять его. Вызов его с нулевым аргументом просто запрашивает значение. Мы могли бы написать

```go
var numCPU = runtime.GOMAXPROCS(0)
```

Будьте уверены, чтобы не путать идеи параллелизма (структурирование программы как независимо выполняющихся компонентов) и параллелизма (выполнение вычислений параллельно для эффективности на нескольких ядрах CPU). Хотя возможности Go для параллелизма могут облегчить некоторые задачи параллелизма, Go — это параллельный язык, а не обязательно параллельный, и не все проблемы параллелизации подходят для параллельной структуры. Подробности смотрите в этом блоге.

#### Буферизованный канал-семафор

Идиомы параллельного программирования можно легко расширить на такие вещи, как разрешение нескольким клиентам использовать объект в любое время. Мы видели, как буферизованный канал действует как семафор. Вот ещё одно применение.

Предположим, у нас есть сервер, который обрабатывает запросы, которые могут использовать ресурсы, такие как подключения к базе данных. И мы хотим ограничить количество одновременных вызовов такого ресурса до `MaxOutstanding`. Обработчик:

```go
var sem = make(chan int, MaxOutstanding)

func handle(r *Request) {
    sem <- 1    // Wait for active queue to drain.
    process(r)  // May take a long time.
    <-sem       // Done; enable next request to run.
}

func Serve(queue chan *Request) {
    for {
        req := <-queue
        go handle(req)  // Don't wait for handle to finish.
    }
}
```

Как только `MaxOutstanding` обработчиков выполняют `process`, больше не принимается ни один входящий запрос, пока один из них не завершится и не освободит место в буфере канала.

Однако этот дизайн имеет проблему: `Serve` создаёт новую горутину для каждого входящего запроса, даже если только `MaxOutstanding` из них могут выполняться в любой момент времени. В результате, если запросы поступают слишком быстро, программа может потреблять неограниченные ресурсы. Мы можем исправить этот недостаток, изменив `Serve` на управление созданием горутин через тот же буферный канал. Это также устраняет вызов `go` из `handle`, поскольку теперь количество запущенных горутин ограничено.

```go
func Serve(queue chan *Request) {
    for req := range queue {
        sem <- 1
        go func(req *Request) {
            process(req)
            <-sem
        }(req)
    }
}
```

#### Мультиплексирование

Возможность `select` в Go позволяет goroutine ждать на нескольких каналах связи. Каждый случай должен быть коммуникационной операцией, возможно, с оператором присваивания; `select` будет ждать, пока один из случаев не сможет выполниться, а затем выполнит этот случай. Если несколько случаев готовы, он выбирает один случайным образом. Синтаксис напоминает `switch`, но все случаи являются коммуникационными операциями.

```go
select {
case <-ch1:
    // ...
case x := <-ch2:
    // ...use x...
case ch3 <- y:
    // ...
default:
    // ...
}
```

Как показано, `select` — это мощный инструмент для управления параллелизмом. Он позволяет получать из нескольких каналов, отправлять в несколько каналов и имеет случайный выбор, если несколько каналов готовы.

`select` с `default` не будет блокироваться. Если ни один из случаев не готов, `default` будет выполнен немедленно. Это полезно для реализации неблокирующих операций.

```go
select {
case <-ch:
    // ...
default:
    // ...
}
```

Мы можем использовать `select` для тайм-аутов. Пример:

```go
select {
case <-ch:
    // ...
case <-time.After(1 * time.Second):
    // timed out
}
```

`time.After` возвращает канал, который поставляет значение после указанной длительности. Если мы хотим ждать на нескольких каналах с тайм-аутом, можно использовать `select`.

Вот пример, использующий `select` для мультиплексирования двух каналов:

```go
func main() {
    c := make(chan int)
    quit := make(chan int)
    go func() {
        for i := 0; i < 10; i++ {
            fmt.Println(<-c)
        }
        quit <- 0
    }()
    fibonacci(c, quit)
}

func fibonacci(c, quit chan int) {
    x, y := 0, 1
    for {
        select {
        case c <- x:
            x, y = y, x+y
        case <-quit:
            fmt.Println("quit")
            return
        }
    }
}
```

Это классический пример использования `select` для управления потоком в параллельной программе. Здесь `fibonacci` продолжает генерировать числа, пока не получит сигнал остановки.

Пример подробного использования `select` в сочетании с таймаутами:

```go
package main

import (
    "fmt"
    "time"
)

func main() {
    c := make(chan int)
    o := make(chan bool)
    go func() {
        for {
            select {
            case v := <-c:
                fmt.Println(v)
            case <-time.After(5 * time.Second):
                fmt.Println("timeout")
                o <- true
                break
            }
        }
    }()
    c <- 1
    c <- 2
    <-o
}
```

### Паника и восстановление (Panic and Recover)

Способ, которым Go справляется с ошибками во время выполнения, отличается от многих языков. Нет исключений (exceptions). Вместо этого есть встроенные функции `panic` и `recover`, с определённой сигнатурой. Как правило, программа не должна паниковать.

Мы видели пример `panic` в одном из ранее определённых примеров нарезки, где некорректное использование приводило к панике во время выполнения. Мы также видели панику в примере `bytes.Buffer.WriteTo`. Паника вызывается вызовом встроенной функции `panic` с аргументом, который обычно является строкой.

```go
panic("something wrong")
```

`panic` — встроенная функция, которая останавливает обычный поток управления и начинает паниковать. Когда функция `F` вызывает `panic`, выполнение `F` останавливается, любые отложенные функции в `F` выполняются нормально, и затем `F` возвращается к своему вызывающему. Для вызывающего `F` ведёт себя как вызов `panic`. Процесс продолжается вверх по стеку до тех пор, пока все функции в текущей goroutine не вернутся, после чего программа завершается. Паники могут быть инициированы вызовом `panic` напрямую. Они также могут быть вызваны ошибками времени выполнения, такими как выход за пределы массива.

Восстановление (recover) — встроенная функция, которая позволяет программе управлять поведением паникующей goroutine. Предположим, что функция `G` откладывает функцию `D`, которая вызывает `recover`, и паника возникает в функции, выполняемой в той же goroutine, что и `G`. Когда выполнение достигает `D` через отложенный вызов, значение, возвращаемое `recover`, будет аргументом, переданным в `panic`. Если `D` возвращается нормально, без новой паники, последовательность паники останавливается. Это означает, что если функция, выполняющаяся внутри отложенной функции, вызывает `recover`, результирующее значение будет сообщением паники, и нормальное выполнение возобновится.

Схематично:

```go
func protect(g func()) {
    defer func() {
        log.Println("done")  // Println executes normally even if there is a panic
        if x := recover(); x != nil {
            log.Printf("run time panic: %v", x)
        }
    }()
    log.Println("start")
    g()
}
```

Здесь `protect` защищает вызов `g` от паники. Отложенная функция проверяет, была ли паника, используя `recover`, и если была, регистрирует её.

Возвращаемое значение `recover` — это либо `nil`, если goroutine не паникует, либо значение, переданное в `panic`. В приведённом выше примере, если `g` не паникует, `x` будет `nil`, и нормальное выполнение продолжится. Если `g` паникует, `x` будет содержать аргумент паники, и `protect` корректно обработает её, зарегистрировав и завершившись.

Это очень мощный механизм. Однако, использовать его следует осторожно. Паника и восстановление — это скорее механизмы для обработки действительно исключительных ситуаций, а не общий механизм обработки ошибок. В Go идиоматично обрабатывать ошибки явно, используя возвращаемые значения, а не панику.

Некоторые примеры использования `panic` и `recover`:

1. **Защита от паники в библиотеке.** Если вы пишете библиотеку и не хотите, чтобы паника в вашем коде распространялась на вызывающую программу, вы можете восстановиться после паники.

2. **Обработка ошибок в глубоко вложенных вызовах.** Если у вас есть функция, которая вызывает много других функций, и все они могут завершиться с ошибкой, вы можете использовать панику и восстановление, чтобы избежать передачи ошибок через все уровни.

Однако, по общему согласию, паника не должна использоваться для обычных ошибок. Ошибки должны быть явно возвращены и обработаны вызывающей стороной.

### Заключение

Этот документ описал основы написания идиоматичного кода на Go. Хотя он не охватывает все аспекты языка, он даёт хорошее понимание стиля и подходов, которые делают код на Go ясным, эффективным и легко поддерживаемым.

Ключевые принципы, которые следует помнить:

1. **Форматирование** — используйте `gofmt`, чтобы не беспокоиться о стиле.
2. **Именование** — короткие, лаконичные, выразительные имена; MixedCaps вместо подчёркиваний; имя пакета как аксессор для содержимого.
3. **Управляющие структуры** — используйте `if` с инициализацией, `for` с `range`, `switch` без fallthrough, type switch для динамических типов.
4. **Функции** — множественные возвращаемые значения для ошибок, именованные результаты как документация, `defer` для управления ресурсами.
5. **Данные** — `new` для обнуления, `make` для инициализации; массивы — значения, срезы — ссылки; карты с идиомой «запятая ok».
6. **Методы и интерфейсы** — методы для значений и указателей; интерфейсы для поведения; встраивание для композиции.
7. **Согласованность** — «Не общайтесь, разделяя память; вместо этого разделяйте память, общаясь»; горутины, каналы, `select`; параллелизм ≠ параллельность.
8. **Паника и восстановление** — только для действительно исключительных ситуаций; предпочитайте явную обработку ошибок.

Для более глубокого изучения языка обратитесь к спецификации языка, «Tour of Go», «How to Write Go Code» и документации стандартной библиотеки.
