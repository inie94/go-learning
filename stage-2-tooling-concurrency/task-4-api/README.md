# README: Тестирование API HTTP-сервера на Go

## 1. Введение

Данный документ описывает техническое задание на разработку комплексных тестов для HTTP-сервера, реализованного на языке Go. Основная цель — обеспечить высокое качество кода, надёжность и устойчивость API-эндпоинтов с помощью современных подходов к тестированию.

В рамках задания требуется реализовать набор тестов, охватывающих все ключевые сценарии работы сервера, с обязательным использованием следующих практик:

- **Table-driven tests** — для параметризации тестовых случаев и улучшения читаемости.
- **Mock-объекты** — для изоляции тестируемого кода от внешних зависимостей (БД, сторонние API, файловая система и т.п.).
- **Subtests** — для логической группировки и независимого выполнения проверок.

Настоящий README служит основой для разработки, содержит детальные требования, ограничения, примеры сценариев, рекомендации по реализации и предложения по улучшению.

## 2. Функциональные требования (к тестируемому серверу)

Хотя основное задание сфокусировано на тестировании, для осмысленного написания тестов необходим чёткий контекст. Предположим, что разрабатывается RESTful API для управления сущностями **«Задача» (Task)** со следующими операциями:

| Метод | Путь               | Описание                                    |
|-------|--------------------|---------------------------------------------|
| GET   | `/tasks`           | Получить список всех задач                  |
| GET   | `/tasks/{id}`      | Получить задачу по идентификатору           |
| POST  | `/tasks`           | Создать новую задачу (принимает JSON)      |
| PUT   | `/tasks/{id}`      | Обновить существующую задачу                |
| DELETE| `/tasks/{id}`      | Удалить задачу                              |

Каждая задача имеет поля:
- `id` (string, UUID) — генерируется сервером.
- `title` (string, обязательное) — название.
- `description` (string, опционально) — описание.
- `completed` (bool) — статус выполнения.
- `created_at` (timestamp) — дата создания.

Сервер хранит данные в реляционной базе данных (PostgreSQL), но для тестов внешняя БД должна быть замокана.

## 3. Технические требования к тестам

### 3.1. Язык и инструменты
- Язык: **Go 1.21+**.
- Тестовый фреймворк: стандартный пакет `testing`.
- Для мокирования: рекомендуется использовать **`gomock`** (или `mockery`) для генерации mock-интерфейсов, либо **`testify/mock`**.
- Для HTTP-тестирования: **`httptest`** из стандартной библиотеки.
- Для утверждений (assertions): **`testify/assert`** и **`testify/require`** (по желанию).

### 3.2. Структура тестов
- Каждый пакет с бизнес-логикой должен иметь соответствующий тестовый файл `*_test.go`.
- Тесты должны быть сгруппированы по функциональности с помощью **subtests** (`t.Run()`).
- Для каждого эндпоинта должны быть реализованы **table-driven tests**, покрывающие:
  - **Успешные сценарии** (HTTP 200/201/204).
  - **Сценарии с ошибками валидации** (HTTP 400).
  - **Сценарии отсутствия ресурса** (HTTP 404).
  - **Сценарии внутренних ошибок сервера** (HTTP 500), когда внешние зависимости возвращают ошибку.
  - **Граничные случаи** (пустые поля, некорректные типы, длинные строки и т.д.).

### 3.3. Изоляция и воспроизводимость
- Тесты **не должны** зависеть от реальной БД или внешних сетевых вызовов.
- Все внешние зависимости должны быть заменены на mock-объекты, реализующие интерфейсы.
- Тесты должны выполняться в любом окружении без дополнительной настройки (кроме установки Go).
- Данные между тестами не должны пересекаться (каждый тест создаёт собственный контекст).

## 4. Ограничения

1. **Использование только стандартных пакетов Go** для HTTP-клиента и сервера разрешено, но допускаются популярные библиотеки (например, `gorilla/mux` или `chi` для маршрутизации) — однако тесты должны работать с любым роутером.
2. **Моки должны быть сгенерированы автоматически** (через `mockgen`), а не написаны вручную — это облегчает поддержку.
3. **Тесты не должны выполняться последовательно**, если это не требуется; они должны быть независимыми.
4. **Покрытие кода** должно составлять не менее **80%** для пакетов, содержащих бизнес-логику и обработчики.
5. **Запрещено** использовать глобальные переменные для состояния тестов.
6. **Тесты должны запускаться** командой `go test ./...` без ошибок и паники.

## 6. Рекомендации по реализации

### 6.1. Архитектура кода для тестируемости
- Выделите бизнес-логику в отдельные сервисы, которые принимают зависимости через интерфейсы (например, `TaskRepository`).
- Обработчики HTTP должны быть тонкими — они только парсят запрос, вызывают сервис и формируют ответ.
- Используйте **внедрение зависимостей** (DI) для передачи mock-репозиториев в тестах.

Пример интерфейса репозитория:
```go
type TaskRepository interface {
    GetAll(ctx context.Context) ([]Task, error)
    GetByID(ctx context.Context, id string) (Task, error)
    Create(ctx context.Context, task Task) (Task, error)
    Update(ctx context.Context, task Task) error
    Delete(ctx context.Context, id string) error
}
```

### 6.2. Написание table-driven тестов
- Определите структуру для каждого набора кейсов, содержащую:
  - `name` — описание.
  - `request` — метод, путь, тело (если есть).
  - `mockSetup` — функция для настройки ожиданий мока.
  - `expectedCode` — ожидаемый HTTP-статус.
  - `expectedBody` — ожидаемое тело ответа (полное или частичное сравнение).
- Используйте `t.Run()` для каждого кейса, чтобы получить отдельные подтесты.

Пример фрагмента:
```go
func TestGetTask(t *testing.T) {
    tests := []struct {
        name       string
        taskID     string
        mockSetup  func(*MockTaskRepository)
        expectedCode int
        expectedBody string
    }{
        {
            name:   "success",
            taskID: "123e4567-e89b-12d3-a456-426614174000",
            mockSetup: func(m *MockTaskRepository) {
                m.EXPECT().GetByID(gomock.Any(), "123e4567-e89b-12d3-a456-426614174000").
                    Return(Task{ID: "...", Title: "test"}, nil)
            },
            expectedCode: http.StatusOK,
            expectedBody: `{"id":"...", "title":"test"}`,
        },
        // ... другие кейсы
    }
    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            // инициализация мока, создание тестового сервера, выполнение запроса
        })
    }
}
```

### 6.3. Мокирование внешних зависимостей
- Сгенерируйте моки с помощью `mockgen` для интерфейса репозитория.
- В тестах создайте контроллер моков (`gomock.NewController(t)`), передайте его в конструктор сервиса.
- Настройте ожидания для каждого кейса с помощью `EXPECT()`.

### 6.4. Использование `httptest`
- Для каждого теста создавайте новый экземпляр HTTP-сервера с помощью `httptest.NewServer()`.
- Передайте в него обработчик с внедрённым mock-репозиторием.
- Выполняйте HTTP-запросы через `http.Client` и проверяйте ответ.

### 6.5. Группировка тестов с subtests
- Для каждого эндпоинта создайте отдельную функцию `TestEndpointName`.
- Внутри неё группируйте табличные кейсы с помощью `t.Run()`.
- Для логического разделения (например, позитивные и негативные сценарии) можно вложить subtests внутрь других subtests.

### 6.6. Управление состоянием
- Каждый подтест должен использовать свежие экземпляры моков и сервера, чтобы избежать влияния между кейсами.
- Используйте `t.Cleanup()` для закрытия ресурсов (сервер, контроллер моков).

## 7. Дополнительные улучшения (возможные расширения)

1. **Измерение покрытия кода** — добавить в CI проверку покрытия (например, с помощью `go test -cover`).
2. **Параллельное выполнение** — использовать `t.Parallel()` для ускорения прогона тестов, где это безопасно.
3. **Интеграционные тесты** — помимо модульных тестов с моками, реализовать интеграционные тесты с реальной тестовой БД (например, в контейнере Docker) для проверки взаимодействия с БД.
4. **Контрактное тестирование** — для клиентов API добавить тесты, проверяющие соответствие OpenAPI-спецификации.
5. **Fuzzing** — добавить fuzz-тесты для парсинга входных данных.
6. **Тестирование производительности** — написать бенчмарки (`BenchmarkXxx`) для узких мест.
7. **Автоматическая генерация тестовых данных** — использовать библиотеки типа `go-faker` для создания реалистичных входных объектов.
8. **Логирование в тестах** — включить отладочное логирование для упрощения анализа упавших тестов.
9. **Запуск тестов с разными флагами** (например, `-short` для пропуска долгих тестов).

## 8. Требования к оформлению кода

- Тесты должны быть хорошо документированы (комментарии к каждой таблице и кейсам).
- Код тестов должен быть поддерживаемым: избегайте дублирования, выносите общие утилиты (создание запросов, сравнение ответов) в вспомогательные функции.
- Названия тестовых функций должны соответствовать шаблону `Test<Component>_<Scenario>` (например, `TestTaskHandler_GetTask_Success`).
- Используйте `t.Helper()` для вспомогательных функций, чтобы упростить трассировку ошибок.
