## 🧪 Задание 1: Пул воркеров — детальное описание

### 📌 Общая концепция

Необходимо реализовать паттерн "пул воркеров" (worker pool) — набор горутин, которые конкурентно обрабатывают задачи из общего канала. Это классический подход для управления параллельной обработкой с ограничением количества одновременных операций.

---

### 🎯 Функциональные требования

#### 1. **Структура пула воркеров**

Должна быть определена структура, содержащая:

```go
type WorkerPool struct {
    workersCount int
    taskQueue    chan Task
    errorCh      chan error
    ctx          context.Context
    cancel       context.CancelFunc
    wg           sync.WaitGroup
    // возможно, дополнительные поля
}
```

#### 2. **Тип задачи (Task)**

Каждая задача — это функция с сигнатурой:

```go
type Task func(ctx context.Context) error
```


#### 3. **Основной функционал**

##### 3.1 **Запуск пула**
```go
func NewWorkerPool(workersCount int, queueSize int) *WorkerPool
func (wp *WorkerPool) Start(ctx context.Context)
```
- Создание указанного количества воркеров (горутин).
- Каждый воркер должен читать задачи из канала `taskQueue`.
- Передача контекста для управления жизненным циклом.

##### 3.2 **Добавление задач**
```go
func (wp *WorkerPool) AddTask(task Task) error
```
- Блокирующая или неблокирующая отправка задачи в канал.
- Должна проверять, активен ли пул (не завершён ли graceful shutdown).
- Возврат ошибки, если пул остановлен или канал переполнен.

##### 3.3 **Graceful Shutdown**
```go
func (wp *WorkerPool) Stop()
func (wp *WorkerPool) StopAndWait()
```
- При отмене контекста (или явном вызове `Stop()`):
  1. Пул перестаёт принимать новые задачи.
  2. Все текущие задачи должны быть обработаны (не прерываются принудительно).
  3. Воркеры завершаются после обработки текущей задачи.
  4. Используйте `sync.WaitGroup` для ожидания завершения всех воркеров.

##### 3.4 **Обработка ошибок**
```go
func (wp *WorkerPool) Errors() <-chan error
```
- Канал для получения ошибок от воркеров.
- Любая ошибка, возвращённая задачей, отправляется в этот канал.
- Паники в задачах перехватываются и преобразуются в ошибки.

---

### 🔧 Технические требования

#### 1. **Обработка паник**
- Каждый воркер должен быть обёрнут в `defer recover()`.
- При возникновении паники:
  - Паника логируется или преобразуется в ошибку.
  - Воркер не должен падать (продолжает работать).
  - Информация о панике отправляется в канал ошибок.

```go
defer func() {
    if r := recover(); r != nil {
        wp.errorCh <- fmt.Errorf("worker panic: %v", r)
    }
}()
```

#### 2. **Управление контекстом**
- Контекст передаётся при создании пула и в каждую задачу.
- При отмене контекста:
  - Воркеры должны завершить текущую задачу (задача сама должна проверять `ctx.Done()`).
  - После завершения всех задач пул останавливается.

#### 3. **Канал ошибок**
- Буферизированный или небуферизированный канал (рекомендуется буферизированный).
- Потокобезопасный доступ.
- Закрывается только после завершения всех воркеров.

### 📋 Пример интерфейса (API)

```go
package main

import "context"

type Task func(ctx context.Context) error

type WorkerPool interface {
    // Start запускает воркеры
    Start(ctx context.Context)
    
    // AddTask добавляет задачу в очередь
    AddTask(task Task) error
    
    // Stop инициирует graceful shutdown
    Stop()
    
    // StopAndWait останавливает пул и ждёт завершения всех воркеров
    StopAndWait()
    
    // Errors возвращает канал для чтения ошибок
    Errors() <-chan error
}
```

### 🧪 Сценарии тестирования

1. **Базовый сценарий**
   - Добавить 10 задач.
   - Проверить, что все выполнились.
   - Никаких ошибок.

2. **Graceful shutdown**
   - Добавить задачи с длительным выполнением.
   - Вызвать `Stop()`.
   - Проверить, что все задачи завершились, новые не принимаются.

3. **Обработка паник**
   - Добавить задачу, которая паникует.
   - Проверить, что ошибка получена в канале.
   - Проверить, что воркер продолжает работу.

4. **Отмена контекста**
   - Передать контекст с `cancel()`.
   - Задачи должны корректно завершаться при отмене.

5. **Переполнение очереди**
   - Установить маленький размер очереди.
   - Попытаться добавить больше задач.
   - Проверить блокировку или ошибку.

### 🏗️ Рекомендации по реализации

#### Вариант с блокирующей отправкой:
```go
func (wp *WorkerPool) AddTask(task Task) error {
    select {
    case <-wp.ctx.Done():
        return errors.New("pool is stopped")
    case wp.taskQueue <- task:
        return nil
    }
}
```

#### Воркер:
```go
func (wp *WorkerPool) worker(id int) {
    defer wp.wg.Done()
    defer func() {
        if r := recover(); r != nil {
            wp.errorCh <- fmt.Errorf("worker %d panic: %v", id, r)
        }
    }()
    
    for {
        select {
        case <-wp.ctx.Done():
            return
        case task, ok := <-wp.taskQueue:
            if !ok {
                return
            }
            // Выполняем задачу с контекстом
            if err := task(wp.ctx); err != nil {
                wp.errorCh <- fmt.Errorf("task error: %w", err)
            }
        }
    }
}
```

#### Graceful shutdown:
```go
func (wp *WorkerPool) Stop() {
    wp.cancel()        // отменяем контекст
    close(wp.taskQueue) // закрываем канал задач
}

func (wp *WorkerPool) StopAndWait() {
    wp.Stop()
    wp.wg.Wait()        // ждём завершения всех воркеров
    close(wp.errorCh)   // закрываем канал ошибок
}
```

### 💡 Дополнительные улучшения (опционально)

1. **Метрики**
   - Количество обработанных задач.
   - Количество ошибок.
   - Время выполнения задач.

2. **Ограничение времени выполнения**
   - Каждая задача может иметь свой таймаут через контекст.

3. **Приоритеты задач**
   - Использование нескольких очередей с разными приоритетами.

4. **Динамическое изменение количества воркеров**
   - Возможность добавлять/удалять воркеров во время работы.

5. **Retry-механизм**
   - Повторное выполнение упавших задач с экспоненциальной задержкой.

---

### ⚠️ Важные моменты

1. **Не блокируйте `Stop()`** — он должен быть неблокирующим.
2. **Закрывайте каналы только в одном месте** — избегайте паники при закрытии.
3. **Используйте `sync.Once`** для гарантии однократного закрытия каналов.
4. **Проверяйте `ok` при чтении из канала** — чтобы корректно обрабатывать закрытие.
5. **Избегайте deadlock'ов** — не ждите воркеров изнутри воркера.

### 📝 Пример использования

```go
func main() {
    ctx, cancel := context.WithCancel(context.Background())
    defer cancel()
    
    pool := NewWorkerPool(5, 10)
    pool.Start(ctx)
    
    // Добавляем задачи
    for i := 0; i < 100; i++ {
        i := i // замыкание
        pool.AddTask(func(ctx context.Context) error {
            time.Sleep(time.Second)
            if i%10 == 0 {
                return fmt.Errorf("error in task %d", i)
            }
            fmt.Printf("Task %d completed\n", i)
            return nil
        })
    }
    
    // Читаем ошибки
    go func() {
        for err := range pool.Errors() {
            log.Printf("Error: %v", err)
        }
    }()
    
    // Ждём завершения
    pool.StopAndWait()
    fmt.Println("All tasks completed")
}
```
